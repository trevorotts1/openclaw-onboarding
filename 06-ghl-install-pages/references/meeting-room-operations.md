# Meeting Room operations — Skill 06 / workflow WF26

Operator reference for `06-ghl-install-pages/tools/ghl_meeting_rooms.py`.
Implements Document 1 §23 and Document 2 WF26 (lines 656-672).

## 1. Capability boundary

No public Meeting Room lifecycle contract is confirmed. A Calendar field for a
meeting location, a physical calendar resource, or a generic room URL is **not**
proof of a video-room create API. Therefore:

- Create/configure runs through Skill 6's existing managed-browser system.
- The operator adopts a public operation only after its exact contract is added
  to the shared registry (`public/operations.py`) by the registry owner (WF00).
- The module never invents an HTTP route, webhook, recording endpoint, transcript
  export, or background job for an internal operation.
- Calendar/Appointment operations stay with Skill 44. This operator asks the
  injected calendar adapter and records only what it observed.

Browser policy is centralised: this operator declares no priority list of its
own. It uses the shared `browser_manager` session plus the shared
`ghl_ab_executor` (Document 1 §21.6).

## 3. Plan model

`plan_room(task)` is network-free and browser-free. It raises `StopAndReport` on a
decision-critical gap rather than guessing.

| Field | Rule |
|---|---|
| `location_id` | Required. The subaccount gate runs before any write. |
| `host_user_id` | Required. **Never** defaulted to the operator identity: a room must belong to the actual authorized host. |
| `purpose` | Room name / intent used for the inventory match. |
| `room_link_mode` | Internal label: `reusable`, `appointment_unique`, `existing_room`. Translate only through observed UI controls or a verified API field. |
| `existing_room_reference` | Required when `room_link_mode=existing_room`. |
| `calendar_id` / `course_id` / `event_id` | Integration branch inputs. |
| `cohost_user_ids` | Identified, authorized staff users only. |
| `participant_audience`, `allow_guests`, `waiting_room_policy` | Admission posture. Controlled admission is the default for private/paid sessions. |
| `passcode_secret_reference` | A **reference**, resolved at run time by an injected resolver. A literal `passcode` in the task is refused outright. |
| `schedule_timezone`, `duration_minutes`, `notice_minutes`, buffers, `recurrence` | Preserve the client's real availability; no hardcoded schedule. |
| `recording_policy`, `transcription_policy`/`_language`, `summary_policy`, `review_owner` | Default OFF / not requested. Enabling needs `approval_references`. |
| `retention_and_sharing_policy`, `notification_policy` | Client policy. |
| `approval_references` | Approval references for recording/transcription. |
| `requested_outputs` | Optional sub-results (screen sharing, recording, transcript, summary, follow-up). |
| `breakout_requested` | Advanced branch, opt-in. |
| `migration_authorization` | Required to replace an existing meeting location (e.g. Zoom). |
| `cleanup_authorization` | Required to delete a scratch room this run created. |

The generated plan also carries `slug`, `created_at`, and `sub_results`.

## 5. Managed-browser sequence

1. **Bind identity** — subaccount and staff user; confirm the signed-in identity may
   configure the intended host's room.
2. **Probe the feature** — distinguish missing entitlement, missing user permission,
   incomplete rollout, and selector drift. Report capture-pending targets.
3. **Inventory existing rooms** — reuse the approved room; never create a duplicate
   per run. A room owned by someone else is never a reuse candidate.
4. **Use the observed setup flow** — documented entry `Meeting Room > My room >
   Create room`; resolve real controls from the live DOM.
5. **Apply only supported controls** — an unsupported requested setting becomes a
   named gap, never a silent drop.
6. **Save and re-open** — read name, owner, link, security and co-hosts back from the
   UI. A toast is not proof.
7. **Configure integration** — calendar, course, event/community, or reusable link.
8. **Verify guest-facing access** — isolated guest context; never the authenticated
   host session.
9. **Authorized rehearsal** — record exactly which capabilities were exercised.
10. **Deliver the correct links** — guest join link vs host/admin controls vs booking
    link are three different things.

Cleanup runs only for a scratch room this run created and only with
`cleanup_authorization`.

## 6. Calendar boundary (hybrid)

Skill 44 owns supported Calendar/Appointment API operations; Skill 6 owns UI-only
Meeting Room configuration and verifies the attendee experience.

- **reusable** — the observed reusable join link is recorded; do not claim
  appointment isolation.
- **appointment_unique** — create two authorized test appointments, read the ACTUAL
  event/notification links, and verify they differ. Identical links mean reusable
  behaviour and must be reported as unverified.
- **reschedule/cancel** — verify the platform's real behaviour; never presume link
  invalidation or regeneration. Report stale/duplicate links as warnings.
- **existing Zoom/location** — preserved unless `migration_authorization` is given.
  No implicit migration, no replacement of recurring events or customer
  notifications.
- Availability source, timezone, duration, lead time, buffers and working hours are
  preserved, including daylight-saving transitions on recurring events.

## 7. Security defaults and approvals

Implementation recommendations, not vendor defaults:

- Controlled admission for private consultations and paid groups.
- Guest access only for an intended outside audience.
- Host/co-host privileges limited to identified, authorized users.
- Recording and transcription OFF unless the client policy says otherwise and an
  approval reference exists.
- Never start microphones, cameras, an instant meeting, or a recording merely to
  prove a control exists.
- Never promise webinar capacity, attendee limits, retention periods, or external
  guest behaviour beyond observed/documented tenant capability.

## 8. Recording, transcription, summary, follow-up

Each output is a **separate** sub-result. Recording alone does not prove transcript
availability; the vendor requires transcription to be enabled during the meeting for
transcript-based features. Post-meeting artifacts are only ever `verified` from an
observed artifact; otherwise they stay `pending`. Temporary processing uses bounded
polling with a resumable pending status, never an infinite loop.

Follow-up tasks are created through Skill 44 by an authorized adapter after human
review of decisions/action items; no invented commitments.

Meeting content is private client data: redact evidence, keep full recordings and
transcripts in approved storage, never in the onboarding repository or another
client's knowledge base.

## 9. Breakout rooms

Optional advanced branch, checked before promising support. Creating a room,
assigning participants, opening rooms, and participants actually moving are four
distinct facts. Report `breakout_opened_verified` only when participants were
observed inside. Never assume main-room recording contains breakout discussion.

## 10. Honest result states

Sub-results (`sub_results`) use `not_run`, `pending`, `verified`, `failed`,
`not_requested`:

```
configuration_saved_and_reopened      host_identity_verified
guest_join_flow_verified              calendar_link_generation_verified
reschedule_and_cancellation_verified  live_audio_video_verified
screen_sharing_verified               recording_verified
transcript_verified                   summary_verified
follow_up_task_creation_verified      breakout_opened_verified
```

Top-line status: `PLANNED` (dry run), `SETUP_VERIFIED`, `VERIFIED`, `BLOCKED`.
Live media: `LIVE_AV_PENDING` or `LIVE_AV_VERIFIED`.

Rules enforced by `finalize_result`:

- A requested but untested sub-result is never `verified`.
- Any requested sub-result in `failed` blocks the run (`BLOCKED`).
- A headless run without usable media devices returns
  `SETUP_VERIFIED / LIVE_AV_PENDING`.
- Devices present but no observed rehearsal is still `pending` — device presence is
  not proof of audio/video.

## 11. Selector capture procedure

Every target in `tools/selectors-live-meeting-rooms.json` starts as
`capture-pending` with `conf: 0`. The D8 gate stops any live run that needs a
pending REQUIRED target; it never becomes a guessed CSS click.

To flip a target to `locked`:

1. Use an authorized test host and subaccount.
2. Open Meeting Room, create a scratch room owned by that test host.
3. Walk each surface and record the real anchor plus confidence in the map.
4. Read the room back after Save.
5. Remove the scratch room under an explicit cleanup authorization.
6. Record the capture date and a location alias — never a client name.

`--selftest` and the tests assert that every click-list target resolves in this map
and that no raw CSS is emitted.
