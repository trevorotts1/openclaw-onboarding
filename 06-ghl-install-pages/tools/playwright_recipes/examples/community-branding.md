# Captured modern community Branding

`community_branding.run_branding(page, inputs, evidence_root,
portal_context=...)` implements the modern native group
`/settings/branding` route. `communities.configure` jobs with `branding` use this
dedicated portal executor; validate with `validate_inputs` and bind host
receipts/replay to `configuration_hash(inputs)` and the exact community slug.

The trusted host captures an opaque `community_portal.capture_context` at the
exact group home using a real authenticated same-session identity reader.
Modern Branding readiness uses the captured Settings link's exact group-bound
`href`; modern Learning uses its Learning link. Those modes do not pretend the
classic Add Channel/uppercase SETTINGS controls apply to the new UI. The same
user, location, portal origin, group name and slug are revalidated on the exact
Branding route before file selection, Save and independent reload.

Supply all three previous image previews in `branding.expected`. A `null` value
requires the positively observed native empty placeholder inside that exact
picker owner; zero image count by itself is insufficient. Each replacement
names one captured `logo`, `favicon` or `cover` picker ID, an absolute local PNG
and approved SHA256. Every source is checked before the first upload, then
copied to a private immutable file. This runner's conservative local size limit
is less than 10 MiB per PNG; that is not a claim about the vendor's limit.

The captured picker opens the native file chooser directly, without a stable
DOM file input. The runner obtains the chooser from that exact click, requires
single-file mode, checks its actual accepted types when provided, and selects
the approved private PNG. It requires a newly observed credential-free HTTPS
preview URL in that exact picker owner. Unexpected crop/upload dialogs or an
unreadable/unchanged preview stop before Save. Unrequested sibling image URLs
must remain unchanged. `Save changes` is followed by an independent native
Branding reload and exact three-preview comparison.

The group-configuration lane shares `community-details-state.json` and the
existing evidence lease, so separate group operations need separate evidence
roots. Intent is recorded before each chooser and Save; uncertain runs retain
observed URLs and refuse a second upload. No group activation, membership
invitation, post, public access or communication is performed.

The outcome stays `NEEDS_VERIFICATION`: `controls_verified:true`,
`independent_readback:VERIFIED`, `functional_verified:false`,
`behavior_verified:false`, `communication_attempted:false` and
`verification_required:true`. It returns bound slot/source/preview hashes rather
than raw private source paths or preview URLs. Root integration must validate
those exact fields before accepting the provider receipt. Source/synthetic
checks are not native Python or member acceptance.

Replace every example path/hash/identity/URL from approved inventory. The
example's null previous previews do not claim the actual target has no images.
Classic community settings, course associations and application-level group
creation have separate captured contracts.
