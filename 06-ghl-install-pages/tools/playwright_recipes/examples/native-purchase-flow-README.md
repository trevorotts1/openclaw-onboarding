# Native purchase flow client

Load `run` from `native-purchase-flow-client.py` using `runpy.run_path`, then call `run(page, manifest_path, probes_path, evidence_root)` with the host's existing authenticated Playwright Page. Prepare the manifest and exact, measured host probes first. The host validates every stage and capture before making a write; it then navigates within the same application origin, uses the normal native recipe for each stage, and journals each stage. Save drafts only. The runtime never publishes or initiates a charge.

A manifest is a JSON object with `location_id`, `route_graph`, `page_bindings` and `stages`. `route_graph` is the complete, approved Skill 49 compiled graph. For every referenced checkout or offer role, `page_bindings[role]` has exactly `status: "PASS"`, `location_id`, `graph_page_id`, `native_page_id`, `native_step_id` and `source`. Obtain the native page and step IDs and the source reference from an independent same-location readback; Skill 49's logical page ID is not a native GHL ID.

Each stage has exactly `id`, `kind`, `role`, `operation`, `inputs` and `depends_on`. Put pages/folder/design work first, followed by native checkout, purchase and decline actions, then confirmation. List earlier stage IDs in `depends_on`. Stage IDs contain only letters, digits, `_` or `-`. For `checkout`, `purchase` and `decline`, use `checkout.configure_native` or, for an extra offer, `checkout.one_click_upsell`. Use the same `location_id` and the bound `native_page_id` in each stage's `inputs` and editor URL. The native checkout inputs require the actual `step_id`, `component_id`, `tab_id`, `frame_name`, `adapter_capture` (a relative path to a real location- and page-bound capture), `family`, `main_price` and `checkout_contract`; see `test_pages_checkout.py` for the exact data shape. The price must be the already verified catalog product and native price, including its real amount, currency and billing terms. The PASS contract must match location, product and price; an upsell contract also binds the verified source/prior payment and the offer step.

For a purchase stage, `purchase_action` is `{"kind":"accept","target_step_id":"<read-back native step for graph paid target>"}`. For the corresponding decline stage, its kind is `decline` and its `target_step_id` is the read-back native step for the graph's explicit-decline target. Both targets are derived by looking up the graph edge's target role in `page_bindings`. Accept and decline must have distinct, independently captured native component IDs: the current adapter stores one action per component, so two stages targeting one component are refused. Do not infer that two controls exist from a fixture; capture and verify them in the actual editor. No URL-navigation button is treated as a purchase action.

A completed stage may report payment verification pending; that is expected. `FLOW_STAGES_COMPLETE` means the requested editor stages finished, not that the buyer journey, publication, payment or delivery passed. Independently test the published journey only with a verified sandbox/test-mode provider, and retain provider records and observed session, branches, duplicate-charge prevention and confirmation evidence. The `verify_journey` helper checks consistency of supplied evidence; it cannot authenticate the source.

Keep the same evidence root for an identical resume. Completed stages are not rerun. A started, failed or interrupted stage requires human/operator reconciliation of its retained journal and native readback before another mutation; changing a stage, graph or mapping under the same journal is refused. Keep one evidence root per run and never bypass an uncertain state by silently changing folders.

`native-purchase-flow-manifest.template.json` demonstrates two distinct U1 accept/decline stage shapes. Every `REPLACE_...` value, the illustrative amount, graph and location are fixtures: replace them with independently verified values before use. It is not live evidence. Extend the staged list with the other graph roles as needed; each offer requires its own correct catalog contract, native control IDs, capture and route mapping.
