**Out-of-pipeline files and re-dispatch (1.3.44).** `scripts/governed_runner.py` still refuses a paid dispatch, installation, publication or Complete while any file in the run is ungoverned or any registered file's bytes changed. Two narrow, honest exceptions exist. (A) The quarantine ledger: the operator (key named by `SF_PIN_AUTHORITY_KEY_FILE`, path only, mode 0600, outside the run) runs `scripts/quarantine_ledger.py add --run DIR --path REL --reason TEXT --approver NAME`, which writes `private/quarantine-ledger.json` entries `{path, sha256, size, reason, quarantined_at, approver, signature}` (HMAC-SHA256 over the canonical entry, the same key and signing as the Skill 49 pin-rotation record). `scan()` reports such a file as `quarantined` (acknowledged out of the pipeline) only while the signature verifies and the file's sha256 and size equal the entry; any change, missing or bad signature, or unavailable key leaves it ungoverned and the refusal stands. A quarantined file is never registered, closed, delivered, installed or published, a registered file cannot be quarantined, and reports print the quarantine count. (B) Stage-scoped supersede: for a paid dispatch of stage S only, a registered file whose bytes changed is accepted when its owning stage is S or downstream of S in `references/stage-contract.json` `depends_on` order (it is about to be regenerated and the stage re-closed); the admission record lists each such file with owner stage and old and new hash as `superseded_mismatch`. A mismatch owned by an upstream or unknown stage still refuses, and nothing else is relaxed. With no ledger the behaviour is unchanged.

**Run state, derived owners and quarantine collisions (1.3.45).** Three further narrow rules in `scripts/governed_runner.py` and `scripts/out_of_pipeline.py`; none loosens the gate for a file that did not come through the pipeline. (1) Run state: the closed list `RUN_STATE_FILES` (`production-request.json`, `image-spend-ledger.json`, `page-result.json`; exact root-level names, registered, valid JSON of the right shape) is rewritten by the pipeline on every dispatch, so a byte change is recorded in the admission decision as `run_state_changed` (old and new sha256) and does not refuse any stage; any other name, the same name in a folder, an unregistered file or the wrong content still refuses. The one brand file the run's own `intake.json` names (`brand_file`, root level, registered under intake, a brand profile with `brand_id`) is recorded the same way as `input_changed`, with the launch and request brand pins that went stale. (2) Owners: inside a shared output directory (`review-pdfs/`) the owner of a changed file is derived from the pass-stage receipts (bytes equal a receipt hash, or a board/manifest sidecar all of whose cited hashes are receipt hashes, or a board image its sidecar names and hashes), never from the path; no proof keeps the registry owner. (3) Quarantine collision: a paid dispatch of stage S lists quarantined paths in S-or-downstream output scope as `quarantined_to_supersede`; register/close of that exact path is allowed only for the owning stage with that admitted admission record (ledger hash unchanged), and close only over bytes the stage wrote after the quarantine.

**Hardened admission (1.3.46, SWB-230).** The SWB-220 attack run broke four 1.3.45 rules; each is closed. (1) Signed admission records: every row the governor writes to `private/governor.json` carries `signed_at` and an HMAC-SHA256 `signature` (operator key file named by `SF_PIN_AUTHORITY_KEY_FILE`, tagged `admission_record`); a consumer ignores an unsigned, edited or foreign-key row. `quarantine_release()` also verifies the ledger entry's signature and re-checks `in_stage_scope` for the exact path and the owning stage, so a record cannot release a path outside the stage's own directories. (2) Render-bound release: closing a quarantined path needs the stage executor's own `<stage>/stage-executor-record.json` to list that exact path with an output sha256 equal to the bytes on disk, written after the signed admission; old bytes, or old bytes plus one byte, are in no executor record and stay refused. (3) Owner derivation uses only what a pass-stage receipt itself lists (the exact path as an `artifact_hashes` key, or an exact file hash); a JSON sidecar, a cited hash inside the file under test or a sibling board record is never evidence, so unlisted `review-pdfs/` files keep their registry owner and keep refusing. (4) A changed declared input (the `brand_file` profile) refuses a paid dispatch, installation, publication or Complete unless a signed input acknowledgement (`scripts/quarantine_ledger.py acknowledge-input --run DIR --path REL --old-sha256 H --new-sha256 H --reason TEXT --approver NAME`, stored in `private/input-acknowledgements.json`) covers exactly that file hash; it is void the moment the file changes again. The closed run-state list of 1.3.45 is unchanged (its attack cases A2 and A7 were refused).

**Admission v3 under threat model M (1.3.47, SWB-240).** The admission gate exists to stop mistaken or unreviewed out-of-pipeline files becoming pipeline output. Threat model M: assume an actor that can WRITE ANY FILE inside the run folder (`governor.json`, any `stage-executor-record.json`, receipts' siblings, sidecar JSON, edited images, the quarantine ledger) but does NOT hold the operator key (`SF_PIN_AUTHORITY_KEY_FILE`, mode 0600, outside the run). Under M anything that is only an unsigned file, field or claim is never trusted; only key-signed records (HMAC-SHA256, each record type with its own tag, bound to exact path + sha256 + stage + reason + approver + time) and the contents of pass-stage receipts written by the gate are. An actor holding the key is the owner and out of scope. 1.3.46 failed six attacks (B08, B09, B10, B14b, B19, B20) because it trusted an unsigned `stage-executor-record.json`, skipped any declared input whose name is also a stage input, and could not see a deleted or rolled-back ledger. 1.3.47 removes every unsigned trust: `render_binds()`, the executor-record binding, the admission-row quarantine release and the byte-equals-a-receipt-hash owner rule are gone. What remains: signed quarantine entries (valid while the hash equals), the owner named by an exact path key in a pass-stage receipt's `artifact_hashes`, the closed run-state list (exact root-level names, JSON of the right shape; it admits no image and records old/new sha256), signed admission records and signed input acknowledgements. New: (1) `scripts/quarantine_ledger.py release-quarantine --run DIR --path REL --stage STAGE --reason TEXT --approver NAME` signs that STAGE may register and close the quarantined path over the bytes on disk now (the operator signs it after the stage regenerated the file; the bytes must differ from the quarantined bytes; the note prints the executor-record row it saw as evidence only and trusts nothing from it), stored in `private/quarantine-releases.json`. (2) `scripts/quarantine_ledger.py reown --run DIR --path REL --owner-stage STAGE --reason TEXT --approver NAME` signs that a registered file as it is now belongs to STAGE (replaces the content-claimed owner rules), stored in `private/reown-records.json`; both records are void the moment the file's sha256 differs from the signed one. (3) `scripts/quarantine_ledger.py seal` signs the exact set of ledger entries in `private/quarantine-seal.json` (needed once for a ledger made before 1.3.47; every later `add` re-seals): a ledger that disagrees with its seal, or an older seal than the anchor stored beside the key (`sf-seal-anchors/`, or `SF_SEAL_ANCHOR_DIR`), is broken and honours nothing, and the seal still names a deleted entry's path. (4) A declared brand file is checked even when its name is a stage input (`brand.json`).

**Run binding, absent-seal refusal and the signed rebind record (1.3.48, SWB-250).** The bar for this chain: the pre-existing admission design (the unsigned `private/governed-outputs.json` registry, the keyless `register_output`/`close_output` calls, and directory scanning that skips symlinked directories) is a KNOWN BASELINE LIMITATION and is out of scope here. It is recorded as a follow-up: a separate hardening that signs the registry (the adversarial review's N01, N02, N03, N04 and N11). Each 1.3.48 change is judged on (1) whether it opens a NEW hole relative to the 1.3.44 baseline and (2) whether the NEW signed records and the seal are sound under threat model M. Three changes. (1) **Run binding.** Every signed record (quarantine entries, the seal, release, reown, rebind, input acknowledgement and every admission row) carries `run` = `{root: the resolved absolute run root, run_id: the run_id stage_gate init writes into private/state.json, or "" when none}` INSIDE its signed payload, and every verifier compares it to the run being scanned. A record signed for run A is void in run B (a copied folder differs by path; a folder recreated at the same path differs by run_id). Under M an actor can rewrite state.json, which only voids records (a denial) and never makes one valid. A run moved to another path needs its records signed again. (2) **Absent seal.** When the operator's anchor outside the run (`sf-seal-anchors/` beside the key, or `SF_SEAL_ANCHOR_DIR`) exists, an absent ledger, an absent seal or an unreadable seal REFUSES, never "nothing was ever quarantined"; every authoritative admission then refuses with source `quarantine_ledger`. Only the operator-signed writers (`quarantine_ledger.py add`, `seal`) create the anchor; scan, register, close, admit and status never do. A 1.3.47 ledger is adopted once with `quarantine_ledger.py seal --adopt-legacy`; 1.3.47 release, reown and acknowledgement records are void and are signed again. (3) **Rebind.** `scripts/quarantine_ledger.py rebind --run DIR --path REL --stage STAGE --reason TEXT --approver NAME` signs that a REGISTERED, emitted file whose bytes changed since the gate attested them (the copy file, `copy/public-copy.md`) is re-attested over the bytes on disk now, in `private/rebind-records.json`. The record is bound to run, path, the registry's old sha256, the new sha256, the owning stage (it must equal the registry's), reason, approver, time and an evidence note; the command prints the gate-written hashes it saw (state.json close hashes, pass-receipt hashes) as evidence only and trusts none of it. It is void the moment the file's sha256 differs from the signed one. It is an OWNER DECISION, not a pipeline pass: every admission decision lists the rebound files (`out_of_pipeline.rebound`, with the basis "owner decision (signed rebind record), not a pipeline pass").

## Python dependency: jsonschema (operator note, never for the client)

`scripts/stage_gate.py` (the style-selection schema check) imports `jsonschema`. On a Homebrew or Debian Python (externally managed, PEP 668) pip refuses a plain or
`--user` install, so the package lives in the shared pydeps folder `<root>/pydeps/py<major>.<minor>/`
(`$OC_PYDEPS_DIR` as-is, else `$OPENCLAW_ROOT`, else `/data/.openclaw` when it exists, else `$HOME/.openclaw`;
`$HOME/.claude/pydeps/py<X.Y>/` is also looked up), installed with `pip install --target`. The file puts that folder on
`sys.path` itself before it imports, so plain `python3` works: no venv, no activation step. Never use
`--break-system-packages`, never create a venv, never tell the client. If the import fails, check with
`bash update-skills.sh --check` and run the one sanctioned fix from `83-black-friday-launcher`:
`python3 -m launcher_core.cli dependencies --install`.
